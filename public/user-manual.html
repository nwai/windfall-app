Windfall App

User Manual  ·  Version 1.1  ·  May 2026

Overview

The Windfall App is an analytical tool for Weekly Windfall lottery number analysis and candidate generation. It provides:

  • Candidate set generation using configurable strategies and constraints
  • Multi-signal scoring of each candidate (Conv, IDM, Stage IDM, Rdy, Win, Nrr, NS)
  • Monthly frequency analysis of drawn numbers
  • Zone pattern analysis, temperature transitions, and Monte Carlo simulation
  • DGA (Draw-Grid Analysis) visualisation
  • Historical prize back-testing

Getting Started

Loading Draw History

The app requires draw history data to power analysis, scoring, simulation, and candidate generation. Use the Draw History Manager panel near the top of the app to load, maintain, and verify your history.

  1. Click Select CSV file….
  2. Choose your history file (typically windfall_history_lottolyzer.csv).
  3. The app parses the file and populates the history-dependent panels automatically.

You can also load history by using Import Draws (CSV/JSON) from the same Draw History section. This is useful when you receive draw history from another tool or from a saved export.

Manual entry and maintenance buttons

  • Load Next Draw — opens the entry form for manually entering a new draw.
  • Save New Draw — writes the currently entered draw to the selected CSV file (or offers a download fallback if direct write access is not available).
  • Select CSV file… — chooses or changes the active history CSV.
Duplicate protection: the app now blocks saving an exact duplicate draw and also blocks saving a second, different result for a date that already exists. This prevents the most common manual-entry mistakes before they reach your history file.
Safari users: If the File System Access API is not available, a standard file picker will appear automatically as a fallback.

WFMQYH Window

WFMQYH is the active draw-history window used by many evidence panels and generation weights. The shortcuts are designed around draw counts rather than calendar labels: Weekly uses 3 draws, Fortnight uses 6 draws, Month uses 13 draws, Quarter uses 36 draws, and Year uses 156 draws.

Why Month is 13 draws: although some calendar months contain 12 or 14 draw dates, 13-draw months are the most common practical monthly shape in the loaded Windfall history. The Month shortcut therefore uses 13 draws as the standard month-like evidence window. Panels that perform calendar-month analysis, such as Monthly Draws Summary and Stage IDM, still calculate the actual expected draw count for the working month where that matters.

History Scopes

Windfall now separates history scopes so diagnostics do not quietly mix short tactical windows with long-run baseline evidence.

  • Current WFMQYH window means the active selected draw window. Tactical panels and generation-weight views use this when the user is intentionally asking, “what does the current selected window say?”
  • Real all history means the loaded real draw history after simulated or fallback rows have been excluded.
  • Windfall baseline history means real all history with the opening partial month removed when that first month is incomplete. This is used for baseline and validation-style panels such as Survival Analyzer, Temperature Transition Diagnostics, Most Likely NOT Drawn, and MLND Backtest Validation.
Truthfulness note: Monte Carlo remains a current-window weighting tool. It is not an all-history calibration panel, and its label shows the WFMQYH scope it is using.

Survival Analysis

Survival Analysis estimates number-level drought return behaviour using a discrete-time drought hazard model with Bayesian shrinkage. In the main app it uses Windfall baseline history, not the active WFMQYH window, so its baseline is not distorted by very small tactical windows.

Monthly Transition Context columns

The Survival table also shows observe-only monthly movement context from the Monthly Bucket Transition Lab. These columns help compare survival drought evidence with the current monthly bucket state, but they do not change Survival ranking, probabilities, selections, or generation weights.

Number Trends Table

The Number Trends Table shows the 45 numbers in nine compact blocks of five numbers. Each row is designed for quick scanning: the number pill, direction arrow, and Δ 3→13 value share the same colour so the recent movement signal is visible at a glance.

What the draw-window counts mean

  • 3D, 6D, 9D, 13D, and 15D count how many of the latest 3, 6, 9, 13, or 15 draws contained that number.
  • 36D, 156D, and All extend the same count across broader history windows.
  • A number is counted once per draw if it appears in the loaded history for that draw.

What the arrow and + / - number mean

The direction arrow compares the number's latest-week rate with its typical-month rate:

(3D count / 3 × 100) - (13D count / 13 × 100)

  • Up arrow — the number's latest 3-draw rate is meaningfully higher than its latest 13-draw rate.
  • Down arrow — the number's latest 3-draw rate is meaningfully lower than its latest 13-draw rate.
  • Flat arrow — the difference is small enough to treat as broadly stable.
  • The + or - value beside the arrow is the percentage-point difference between those two rates. For example, if a number appears in 2 of the last 3 draws and 3 of the last 13 draws, the calculation is 66.7% - 23.1% = +43.6. A negative value means the latest 3-draw rate is below the 13-draw rate.
Truthfulness note: this is a recent-vs-broader-history diagnostic, not a calibrated probability or guarantee that a number is due to appear. Use it as movement evidence alongside the other panels.

Clicking a number row marks or unmarks that number for forced inclusion in candidate generation.

Trend Ratio Diagnostics

Trend Ratio Diagnostics records the observed Up / Down / Flat trend composition of historical draws. Each ratio is written as U-D-F, where the three numbers count how many of the eight drawn values were classified as Up, Down, or Flat at that point in history.

Scope and timing

  • The ratio uses mains + supplementary numbers, so every valid ratio totals 8.
  • For each historical draw, the app classifies trend state using only values available before that draw. This protects the diagnostic from lookahead leakage.
  • The table includes all 45 possible U/D/F ratios, even when a ratio has zero observed historical occurrences in the active WFMQYH window.

What z means

The z column compares the observed count for each ratio with a neutral multinomial reference built from the observed Up, Down, and Flat rates. A larger absolute z value means that ratio appeared more or less often than the neutral reference would expect.

Truthfulness note: z is a diagnostic, not a calibrated probability. It is useful for spotting unusual historical structure, but it does not guarantee that a ratio is due or likely in the next draw.

What the Add button does

The Add button toggles a ratio into the active generation filter. The default state is off: when no ratios are selected, all trend ratios are allowed. Click Add once to turn a ratio on; click the same button again when it shows On to remove that ratio and return it to the off/default state.

When one or more ratios are selected, candidate generation rejects candidates whose current Up / Down / Flat composition does not match one of the selected ratios. Trace output reports the active selected ratios, lookback, threshold, historical coverage, and trend-ratio rejection count.

Smart History Review

Under the Draw History Manager, the app includes a Smart History Review panel. This is designed to help you correct human-made history problems without editing CSV files by hand.

What it detects

  • Exact duplicate draw — the same date and the same 6 main + 2 supplementary numbers appear more than once.
  • Conflicting entries for one draw date — two or more rows share the same draw date but contain different numbers.
  • Same number set appears on multiple dates — the exact same numbers appear on more than one date. This can happen naturally, but it is rare enough to review for copy/paste mistakes.

Available review actions

  • Remove exact duplicates — safely removes repeated copies of identical rows while keeping the first occurrence.
  • Keep this version — when two rows share a date, keep the correct one and remove the others for that date.
  • Edit — opens an inline editor so you can correct the date and/or numbers directly inside the app.
  • Delete — removes the selected row from the current loaded history.
Important: if Smart History Review shows same-date conflicts, review them before relying on analysis panels. Two different results on the same date will distort bucket counts, DGA columns, and any logic that depends on recent history.
Saved across refresh: once you remove duplicates, keep a preferred version, edit a row, or delete a conflicting row in Smart History Review, the corrected draw history is cached locally by the app. That reviewed state is restored automatically after a browser refresh, even if you have not yet reloaded from an external source.

Typical correction workflow

  1. Load or import your draw history.
  2. Use Remove exact duplicates first if offered.
  3. Review each same-date conflict and either Keep this version or Edit the mistaken row.
  4. Review repeated-number warnings on different dates to rule out copy/paste errors.

Worked examples

Example 1 — removing an accidental duplicate

Suppose your history contains these two rows:

  • 10/27/25 · Main 1, 8, 17, 25, 31, 44 · Supp 6, 39
  • 10/27/25 · Main 1, 8, 17, 25, 31, 44 · Supp 6, 39

Smart History Review will flag this as an Exact duplicate draw. Click Remove exact duplicates and the extra copy is removed while the first version is kept.

Example 2 — correcting a same-date number-entry mistake

Suppose the same draw date appears twice but one row contains a typo:

  • 10/29/25 · Main 3, 12, 18, 24, 33, 41 · Supp 7, 15
  • 10/29/25 · Main 3, 12, 18, 26, 33, 41 · Supp 7, 15

This is shown as a Conflicting entries for one draw date warning. If you know the first row is correct, click Keep this version on that row. If neither row is exactly right, click Edit and enter the correct numbers before saving the correction.

Official / Reference Source Comparison

The Draw History Manager also includes Compare Against Official / Reference Source. This workflow is specifically designed for situations where direct live access to official sites may be blocked. Instead of relying on live fetches, you can paste or upload source material and compare it locally inside the app.

Accepted source formats

  • Standard draw-history CSV
  • JSON exports, including theLott-style result payloads
  • Saved HTML pages or copied HTML table content
  • Copied plain-text table rows that contain a date followed by 8 numbers

How to compare a source

  1. Open the Draw History Manager.
  2. In Compare Against Official / Reference Source, either:
    • click Upload source file…, or
    • paste the source content into the large text area.
  3. Click Compare source to local history.
  4. Review the comparison summary and the per-date actions.

Comparison result types

ResultMeaning
Exact matchesThe same draw already exists locally for that date.
Missing locallyThe source contains a draw date/result that does not exist in your local history.
Same-date conflictsYour local history and the source both contain that date, but the numbers do not match.
Local-only datesYour local history has dates that are not present in the pasted/uploaded source. These are shown for review only because the source may be incomplete.

Safe correction actions

  • Add this draw — adds a source draw that is missing locally.
  • Use source row for this date — replaces the local row for that date with the source row when the source provides one clear version.
  • Apply safe corrections — batch-applies missing source rows and one-to-one same-date replacements.

Worked example

Assume your local history says:

  • 10/31/25 · Main 4, 9, 16, 23, 35, 42 · Supp 7, 18

But a copied result from an official/reference source says:

  • 10/31/25 · Main 4, 9, 16, 23, 36, 42 · Supp 7, 18
  1. Paste or upload the source content.
  2. Click Compare source to local history.
  3. The app will show a Same-date conflict for 10/31/25.
  4. If the source row is the correct one, click Use source row for this date.

For a broader refresh, you can instead click Apply safe corrections. That will add missing source rows and replace only the dates where the source gives one clear replacement row.

Why “safe” corrections? The app will not automatically delete local-only dates from a pasted/uploaded comparison, because your source may only cover part of history. Local-only dates are therefore treated as review items, not automatic removals.
Recommended use: if you copy results from theLott or Lottolyzer, paste them into this compare area first. Use it to confirm missing rows or date mismatches before making manual edits.

Generated Candidates Panel

The Generated Candidates panel is the main working area. After clicking Generate, it displays a table of candidate number sets with a rich set of analytical scores.

Final survivor selection

When Overgen × creates a larger accepted pool than the requested Count, Windfall must choose which accepted rows survive into the visible table. Active ranking terms can include OGA, month-end carry-over, Scoring Diagnostics influence, odd/even quota selection, and the optional SelHits / RecentHits switches in Recency & Latest Draw Rules. SelHits and RecentHits default OFF; their numeric weights only matter after their switches are turned on. The Trace panel records the active survivor-selection signals for each run.

Truthfulness note: if no survivor-ranking signals are active, Windfall preserves the generated order instead of silently using selected-number or latest-draw overlap as hidden tie-breakers.

Copy candidates for Paste-Weighted input

Use Copy candidates to copy the current generated-candidate table rows as comma-separated lines, ready to paste into the Paste-Weighted Candidate Generator. The copy action uses the current sort/filter view and copies the six Main numbers only, one candidate per line.

Why mains only: Paste-Weighted Candidate Generator is a six-main-number weighting tool. Supplementary numbers are intentionally omitted so pasted rows remain clean six-number inputs.

Stop and show partial

While the main generator is running, Windfall shows a Stop and show partial button beside Generate. Use it when high Attempts × or Overgen × settings make generation take longer than intended.

  • The button stops the active generation worker.
  • If any candidates have already been accepted, Windfall displays the latest accepted partial set through the normal candidate table, scoring, filters, and Trace output.
  • If no candidates have been accepted yet, generation stops cleanly and Trace records that no partial candidates were available.
Truthfulness note: partial output is simply the accepted candidates available at the moment generation was stopped. It is not a completed full run and may contain fewer rows than the requested Count.

PNUaRW45 / RwR45 Random Coverage Mode

PNUaRW45 is a special random coverage mode in the main Generated Candidates panel. The toggle is labelled RwR45.

  • When OFF — the normal candidate generator is used and the Count input controls how many candidates are requested.
  • When ON — the normal Count value is ignored and the app creates exactly 7 candidates.
  • The generator shuffles numbers 1–45 uniformly at random.
  • Hard exclusions are removed before random fill. Forced inclusions are seeded into every candidate, matching the normal generator’s forced-number contract.
  • When no hard constraints are active, the first 42 numbers are split into seven non-overlapping six-number main sets, so main numbers are globally without replacement across the 7 candidates.
  • When forced inclusions or exclusions are active, global-without-replacement applies to the remaining non-forced main filler numbers where possible. If the active constraints make the original strict partition impossible, Windfall uses a row-safe random fallback that still avoids duplicates inside each candidate and still respects exclusions.
  • With no hard constraints, the remaining 3 numbers become the supplementary pool. Under constraints, the preferred supplementary pool is the unused eligible remainder, with row-safe fallback if needed.
Truthfulness note: PNUaRW45 is random coverage, not a prediction, score, or evidence-weighted strategy. While RwR45 is ON, Count, odd/even quotas, scoring influence, and most evidence filters are bypassed. Hard forced inclusions and hard exclusions, including MiAN hard exclusions where active, are honored before the random fill.
The 3 leftover numbers cannot fill all 14 supplementary positions globally without reuse. In unconstrained RwR45, Windfall therefore keeps the main numbers strictly global-without-replacement and reuses the 3-number supplementary pool row by row.

Paste-Weighted Candidate Generator

The Paste-Weighted Candidate Generator lets you paste any number of six-number rows, counts how often each number appears, and then generates mains-only candidates weighted toward the most common pasted numbers.

Adaptive shape

Adaptive shape is a history-aware profile for the six main numbers. It does not score individual numbers. Instead, it describes the candidate's structure by splitting the six mains into:

  • S — single-digit numbers, 1–9
  • D — double-digit numbers, 10–45

Each side is written as odd:even, so the full label is:

S<single-digit odd>:<single-digit even> D<double-digit odd>:<double-digit even>
Adaptive shapePlain-English meaning
S0:0 D4:2No single-digit numbers. Six double-digit numbers: 4 odd and 2 even.
S0:1 D2:3One single-digit even number. Five double-digit numbers: 2 odd and 3 even.
S1:0 D3:2One single-digit odd number. Five double-digit numbers: 3 odd and 2 even.
S0:0 D3:3No single-digit numbers. Six double-digit numbers: 3 odd and 3 even.
S0:2 D2:2Two single-digit even numbers. Four double-digit numbers: 2 odd and 2 even.
S0:0 D5:1No single-digit numbers. Six double-digit numbers: 5 odd and 1 even.

The percentage beside each profile, such as S0:0 D4:2 (12%), is the learned target share from draw-history evidence. It is not a guaranteed probability of the next draw. The app builds this evidence from the active WFMQYH history; when that active window is small, it shrinks the estimate toward the latest 50 draws so the filter stays current without overreacting to a tiny sample.

Observe only vs Quota filter

  • Observe only — generates candidates normally and reports which adaptive shapes appeared in the output.
  • Quota filter — uses the learned percentages as accept/reject quotas, so the final generated candidates try to follow the same shape distribution.

Important: Only Quota filter mode uses the full profile distribution. Observe only mode reports what the generated rows happened to contain.

Quick reading: adaptive shape is a more detailed version of odd/even balance. It asks not only "how many odd and even numbers?", but also "are those odd/even numbers coming from single-digit or double-digit ranges?"

Stage IDM vs Monthly Acceptance Needs

The paste-weighted generator has two separate monthly-bucket controls because they answer different questions:

  • Stage IDM bucket mix is an exact six-main composition filter. Its default is derived from the Stage IDM target and reconciled to six mains because paste-weighted candidates do not include supplementary numbers.
  • Monthly Acceptance Needs uses the literal minimum counts selected in Monthly Draws Summary. For example, 0x≥2 · 1x≥1 means every accepted paste-weighted candidate must include at least two undrawn numbers and at least one 1x number.

Monthly Acceptance Needs is not rescaled. If the selected requirements total more than six, the paste-weighted generator shows an impossible-for-mains-only warning instead of silently changing the user's selected needs.

Honesty note: Stage IDM is a descriptive stage-alignment filter. Monthly Acceptance Needs is a literal user-selected requirement filter. Neither should be read as a calibrated next-draw probability.

Portfolio Compression / 12-Game Distiller

The Portfolio Compression / 12-Game Distiller helps reduce a group of generated or pasted rows into a six-number core plus alternates. It starts with count compression: numbers that appear more often across the supplied portfolio rows rise to the top.

This panel is best used as a decision-support layer. It helps answer: "if I already have a portfolio of candidate rows, which numbers are carrying the most repeated support across that portfolio?" It does not prove that those six numbers will be drawn.

Rows counted is every pasted or loaded row containing at least one valid number. Valid game rows is stricter: rows must contain exactly 6 or 8 unique in-range numbers. Rows needing review are still counted, but the panel flags them so malformed input cannot pass silently.

Load current generated candidates loads generated rows from the main and paste-weighted generators. Supplementary numbers are included when the source provides them; paste-weighted rows are usually mains only.

Optional evidence columns are observe-only and labelled by scope. For example, hot/cold uses mains + supps, while adjacent combos and window shape are mains-only diagnostics. These columns do not change the top-six core.

Structural Strategy Backtest

Structural Strategy Backtest is a validation tool, not a number-picking oracle. It tests a separate historical structural-state strategy against simpler controls. It does not validate the pasted portfolio core currently shown above it.

Core question: when this structural-state method is tested walk-forward, using only past draws at each point, does it behave better than simple frequency or random?
OutputHow to read it
Walk-forward results The number of historical draws tested out-of-sample. More evaluated draws gives a more stable read.
Structural vs simple prize delta Structural-state method minus simple historical-frequency method. Positive is encouraging, but should not be trusted by itself.
Structural vs simple p-value The main honesty metric for structural-state versus simple frequency. Below 0.05 is interesting, 0.05-0.10 is worth watching, and above 0.10 is weak evidence.
Random-history diagnostic p-value Checks whether the structural-state strategy's historical score is unusual compared with random 6/45 histories. A high value means the result sits inside normal luck.
Prize score Synthetic scoring using the backtest prize table. It is useful for comparing strategies, but it is not a money or profit claim.
Mean matches Average number of matching mains per tested draw. This is often more stable than prize score.
3+ hit rate Share of tested draws where the strategy matched at least three mains. Useful because one rare large hit can distort prize score.
Sharpe / Sortino / Calmar Stability diagnostics in synthetic prize-score units. They help compare smoothness and drawdown, but they are not financial investment metrics.
Equity and drawdown curves Visual stability checks. Look for whether compressed improves steadily or only spikes once and then gives the gain back.

Recommended workflow

  1. Use 10,000 Monte Carlo histories for serious reading.
  2. Run several training-window settings, such as 24, 36, 50, 75, and 100.
  3. Look for stability across settings, not one lucky result.
  4. Prefer results where the structural-state strategy has a positive prize delta, higher mean matches, higher 3+ hit rate, lower or comparable drawdown, and a low p-value.
  5. Be suspicious if prize score is the only strong metric. That can be caused by one lucky historical spike.
  6. If simple frequency beats the structural-state strategy, listen to that result. It means the structural layer is not currently adding evidence.
Rule of thumb: the useful signal is not "structural won once." The useful signal is the structural-state method repeatedly outperforming simple frequency across settings, with better 3+ hit rate and a respectable p-value.
Honesty note: use the backtest to decide whether structural-state evidence deserves attention. Do not use it to force belief in the pasted portfolio core or final six.

NS Column — Styling Guide

The NS (NumSum Score) column shows a percentile rank (0–100) of the candidate's total number sum compared against all historical draws. A score of 50 represents the median historical sum.

The column uses colour and font weight to communicate signal strength at a glance:

StyleConditionMeaning
⭐ bold teal on teal tint background Highest NS in the current table Best number-sum candidate in the pool
semi-bold teal on light teal tint NS ≥ 65 (not the single best) Top-tier: sum is significantly above the historical median — historically associated with prize winners
Teal text NS ≥ 72 Very high percentile — sum is in the upper ~28% of all historical draws
Blue text 60 ≤ NS < 72 High — above median, in the upper 40%
Green text 48 ≤ NS < 60 Near-median — roughly average range
Grey text NS < 48 Below median — lower-valued numbers relative to history
In plain English: Teal / bold → the candidate's numbers add up to a total that is higher than most historical draws → historically this is where prize winners tend to cluster. Blue → above average total, good signal. Green → around the median, neutral. Grey → below-average number sum relative to history.

The colour ramp goes: grey → green → blue → teal, where teal is the strongest positive signal.

How NS is calculated

  1. For every historical draw, sum all 8 numbers (6 main + 2 supplementary).
  2. Sort those sums into an ordered list.
  3. For a candidate, compute its total sum and find what fraction of historical draws had a sum less than or equal to the candidate's sum.
  4. Multiply by 100 to produce a percentile: NS = (# historical sums ≤ candidate sum) / (# draws) × 100

NS is wholly independent of Conv, IDM, Rdy and Nrr — it adds a pure "number-value gravity" axis derived from the actual draw history.

Win Column & WinScore

The Win column displays a tier letter (A / B / C / D) and a numeric score. It ranks generated rows by candidate-pool diagnostics without needing Manual Prize Check.

Recalibrated model (April 2026)

Internal analysis of 71,000 generated candidates found that the 2x bucket count (numbers drawn exactly twice in the current month) had the strongest observed association in that candidate sample. Treat the lift values below as sample diagnostics, not calibrated next-draw probabilities.

TierGate conditionObserved sample lift
A2x bucket count ≥ 3~6× baseline
B2x bucket count = 2~4× baseline
C2x bucket count = 1~2× baseline
D2x bucket count = 0baseline

Within each tier, the score is refined by |Conv| magnitude (how much the candidate would move the monthly distribution). Sort the Win column descending (▼) to bring the highest diagnostic rows to the top.

For the strongest combined signal, use the ⭐ Rec button which adds Nrr as a secondary tiebreaker.

Nrr Column — Number Rarity Rank

Nrr scores candidates by how rare their numbers are within the generated candidate pool.

Numbers that barely survive constraint filtering — "contrarian picks" — were overrepresented in one internal candidate-sample analysis. Treat any lift figure as sample-specific and uncalibrated unless confirmed by fresh walk-forward testing.

Algorithm

  1. Count how often each number 1–45 appears across all generated candidates.
  2. For each number: Rarity = MaxFreq − Freq(number)
  3. Nrr for a candidate = sum of Rarity scores for all 8 numbers, normalised to 0–100.

Higher Nrr = rarer numbers in the generated pool. Sort descending (▼) when you want a rarity-based tiebreaker, not a guaranteed predictive signal.

Conv Column — Convergence Score

Conv measures how much drawing this candidate would move the current month's bucket distribution toward (+) or away from (−) the robust Monthly Draws Summary target.

  • Green text = positive Conv (draw moves distribution toward the Monthly Draws Summary target)
  • Red text = negative Conv (draw moves distribution away from the Monthly Draws Summary target)
  • ⭐ marks the highest absolute Conv in the table
Important: Statistical analysis showed that Conv direction (positive vs negative) does NOT predict prize-winning candidates — both positive and negative Conv winners occur at equal rates. A Div 2 winner was observed at Conv = −8.0. Conv is informational and shows distribution impact; it is not directionally predictive on its own. The magnitude of Conv (|Conv|) does carry a modest 2.25× lift.

IDM% Column — Ideal Draw Match

IDM% measures how closely the candidate's bucket composition matches the Ideal pick mix emitted by Monthly Draws Summary. That ideal mix is computed by exhaustive SSD (Sum of Squared Deviations) search against the panel's robust, reconciled monthly bucket target. IDM is a descriptive alignment score, not a probability or guarantee.

  • 100% = perfect match to the ideal composition
  • Blue text (≥ 87.5%) = excellent alignment
  • Green text (≥ 50%) = good alignment
  • Grey text (< 50%) = poor alignment

The Ideal draw composition (IDM target) banner above the table shows the shared Monthly Draws Summary ideal composition (e.g., 0x=5, 1x=2, 2x=1), using the same effective month state as that panel.

Stage IDM Column — Stage-Conditioned Ideal Draw Match

Stage IDM measures how closely a candidate's bucket composition matches the next draw-stage ideal composition emitted by Monthly Draws Summary. It uses comparable historical months with the same expected number of draws, then looks only at the stage we are planning for.

Example: if the working month is a 13-draw month, five draws have already happened, and the next draw is draw 6, Stage IDM learns from historical 13-draw months after their sixth draw. The score then asks: "does this candidate have the bucket mix that would best align with that stage-conditioned target?"

  • 100% = perfect match to the Stage IDM target composition
  • Blue text (≥ 87.5%) = excellent stage alignment
  • Green text (≥ 50%) = good stage alignment

This control lives inside Generation Constraints. It lets you enforce the percentage split between:

The Count against selector changes how many positions are included in the rule:

  • Mains only — the rule is applied over 6 numbers
  • Main + supps — the rule is applied over 8 numbers

How the exact counts are derived

The generator converts the selected percentage into exact counts per candidate:

  • Single-digit count = floor(percentage × counted slots)
  • Two-digit count = remaining counted slots

Example: if Single-digit % = 25%, then Two-digit % = 75% automatically.

  • Mains only (6 numbers) → 1 single-digit + 5 two-digit
  • Main + supps (8 numbers) → 2 single-digit + 6 two-digit
The app shows this exact target directly under the selectors so you can see the real candidate composition implied by the chosen percentage and scope.

Strict enforcement

This is a hard generation rule. Candidates that do not match the exact single-digit / two-digit target are rejected during generation.

Because candidates are made of discrete slots, some percentage choices map to the same exact count. The displayed target is the real rule that will be enforced.

MiAN — Must Include from Acceptance Needs

The Must Include from Acceptance Needs (MiAN) toggle requires every accepted candidate to contain at least a specified count of numbers from each monthly frequency bucket.

Synced mode

When "Use these counts when constructing candidates" is ON in Monthly Draws Summary, the MiAN values are automatically synced from the "Acceptance needs" row — they become read-only (shown with a green tint and 🔗 sync notice). This ensures MiAN always reflects the actual selections made in Monthly Draws Summary.

In this synced mode, the same bucket counts are used in two places:

  • Constructive fill — used while building candidates.
  • MiAN post-filter — checked again after candidates are generated.

This means constructive fill tries to steer candidates toward the required monthly bucket mix, and MiAN then acts as a final guard to reject any candidate that still misses those minimum bucket counts.

When constructive fill is OFF, the 9 bucket count inputs are fully editable.

Hard exclude zero-count buckets

When this sub-toggle is enabled, all numbers in buckets whose required count is 0 are excluded from the candidate number pool entirely before constructive fill and before the normal weighted generation step. This is a stronger constraint than the acceptance filter alone.

Example: if the required counts are 2x = 0, 3x = 0, and 6x = 0, then every currently eligible number in those monthly buckets is removed from the generator pool before any candidate numbers are chosen.

Monthly Repeat Bias

Boosts the selection probability of numbers drawn exactly once this month (the 1x bucket). Use this as a configurable historical bias toward possible monthly repeats, not as a guarantee that 1x numbers will repeat before month-end.

  • Boost factor — how many times more likely a 1x number is to be selected (1 = no boost, up to 10).
  • Include supplementary numbers — if checked, the boost also applies when filling supplementary positions.

Month-end carry-over bias

This toggle reuses the Month-end carry-over study as an actual weighting signal rather than just a display panel.

  • When ON — numbers in the active carry-over pool can receive extra or reduced weighting during candidate generation, and candidate ranking can include a carry-over component.
  • Influence — choose Light, Normal, or Strong to control how far carry-over weights move away from neutral and how much ranking influence they receive.
  • Signal sources — use separate checkboxes for still-undrawn month-end numbers and last-to-first boundary repeats. This lets you keep the more direct undrawn signal while turning off boundary-repeat evidence if it feels too speculative.
  • Clicked boost — when carry-over numbers are clicked from the month-end bucket panel, choose Normal, Strong, or Near-forced instead of always using one fixed massive boost.
  • Automatic default — the toggle defaults ON only while the next draw still falls inside the first 3 draws of the planning month and at least one active carry-over number has a positive learned weight. If all active weights are neutral or penalties, the default stays OFF.
  • Planning month logic — if the current calendar month already looks complete, the app can treat the upcoming month as the planning month, so the carry-over toggle can default on again for the next month boundary.
The panel now labels active weights as boosts or penalties. For example, 13×0.93 penalty means number 13 is in the active carry-over pool, but the learned evidence slightly reduces its generation/ranking influence rather than favouring it.

Last Draw Match Controls

These controls live together in Candidate Generation Influences → Composition & Recency. They all refer to the single most recent real draw in the active WFMQYH window, but they do not all behave the same way.

  • Minimum matches to last draw is a strict lower-bound filter. If it is set to 2, every accepted candidate must contain at least two numbers from the latest draw.
  • Maximum matches to last draw is a strict upper-bound filter only when its checkbox is ON. If it is set to 3, candidates with four or more latest-draw numbers are rejected.
  • Last-draw match bias is not a strict filter. It is a soft weighting strength from 0 to 5. 0 is off; 5 is the strongest setting.

The bias changes direction depending on the minimum setting. If Minimum matches to last draw is 0, a positive bias penalises latest-draw numbers during weighted sampling. If the minimum is greater than 0, the bias favours candidates with stronger latest-draw overlap after they have already passed the strict minimum.

Truthfulness note: Last-draw match bias does not mean "only choose numbers from the last draw." The strict include/exclude behaviour comes from the minimum and maximum match controls.

Look back over newest draws is separate from the single last-draw controls. It builds a wider pool from the newest W draws inside the active WFMQYH history. Its default value follows the latest observed month's completed draw count, not the total WFMQYH size. If the active WFMQYH window is smaller than that month count, Windfall caps the effective W to the available active draws.

Stage IDM

Stage IDM is a second Ideal Draw Model that conditions the target on the current month stage. It first identifies the working month, estimates or uses the selected expected draw count for that month, then computes the next planning stage from the number of draws already loaded.

It then filters history to comparable prior months with the same expected draw count and enough draws to reach the planning stage. From those comparable partial-month states, it builds a robust bucket target and computes an ideal 8-number bucket mix by exhaustive SSD minimisation.

The Expected Draw Count selector can be left on Auto or set manually. Auto infers the expected count from the recent draw weekday rhythm; manual override is useful when you already know the month will contain a specific number of draws.

How to use it: compare the normal IDM target with the Stage IDM target. When they disagree, Stage IDM is usually answering the narrower question: "what does this stage of a like-sized month tend to need now?"
Thin evidence warning: if only a small number of comparable months exist, treat the Stage IDM target as exploratory. The panel will show a warning rather than pretending the evidence is stronger than it is.

The Monthly Bucket Transition Lab is an observe-only research panel for studying how numbers move through monthly buckets: Undrawn → 1x → 2x → 3x → 4x → 5x → 6x → 7x → 8x+.

Baseline scope: the lab uses real draw history and removes the opening partial month from transition baselines. In the bundled history this means 2024-05 stays visible elsewhere, but is excluded from this lab's learned baseline because it is not a complete month. Unlike Stage IDM, which compares a candidate to a stage-conditioned target shape, the Transition Lab works from before-draw states. For each historical draw it records every number's bucket before the draw, whether that number was drawn in that draw, and what bucket it moved into afterward. That lets the app measure transition behaviour such as:

  • how often an Undrawn number breaks into 1x at each draw stage,
  • how quickly numbers reach upper buckets such as 3x, 4x, 6x, or 8x+,
  • whether 13-draw and 14-draw months finish with different bucket shapes,
  • whether prior hot/cold status changes the next-draw hit rate inside the same monthly bucket.

How to read the lab

Read this panel as a movement diary, not as a prediction panel. It is designed to show how numbers have historically moved from one monthly bucket state to another.

  1. Start with Evidence Length. Auto usually means the lab is comparing against same-length months, such as 13-draw months. All lengths pools every baseline month. For monthly-bucket behaviour, Auto is usually the cleaner first read.
  2. Read Current-Stage Transition Expectation next. This is the most immediately useful table. Focus on Count now, Trials, Smoothed rate, and Expected next hits. For example, if Undrawn has 18 numbers now and Expected next hits is 3.1, the lab is saying that historically about three next-draw numbers might reasonably come from currently undrawn numbers at this stage.
  3. Use Undrawn Survival / Break Curve for carry-forward behaviour. Look for where the median undrawn count falls sharply. If it tends to drop between D6 and D9, that supports the observation that undrawn carry-over often breaks around the middle to later-middle part of the month.
  4. Use Upper-Bucket First Reach Timing for rarity checks. This table helps answer questions such as whether 4x by D6 is early, whether 6x+ mostly appears in longer months, and what bucket levels are normal by the current stage.
  5. Use Month-Length Final Shape Comparison for 13d versus 14d questions. This table uses completed months only and is the safest place to inspect whether longer months finish with fewer undrawn numbers or more upper-bucket numbers.
  6. Use Prior Heat x Monthly Bucket Relationship last. This checks whether hot/cold status adds information inside a monthly bucket. If Hot / Undrawn has a higher smoothed rate than Cold / Undrawn, heat may add useful context. If the rates are similar, heat is probably not adding much for that bucket movement.
Rule of thumb: trust Smoothed rate over raw rate, rows with more Trials over thin rows, same month-length evidence over pooled evidence, and repeated patterns across multiple tables over one interesting-looking row.
Coherent story example: if Current-Stage Expectation says Undrawn has high expected next hits, the Undrawn Survival curve shows this stage usually breaks several undrawn numbers, and Upper-Bucket Timing shows the current upper-bucket shape is not already overextended, the lab is giving a stronger, more internally consistent signal.

Constructive Fill

The "Use these counts when constructing candidates" checkbox passes the Acceptance needs counts to the generator as hard requirements. When ON:

  • Every generated candidate must contain at least the specified count from each bucket.
  • The MiAN values in Candidate Generation Influences are automatically synced (see MiAN).

How numbers are chosen from a bucket

During constructive fill, the generator receives:

  • bucket counts — how many numbers are needed from each bucket, and
  • bucket sets — all currently eligible numbers in each bucket.

If a bucket contains more numbers than required, the generator picks from that bucket by uniform random sampling without replacement.

Examples:

  • 1x 5/17 means the generator needs 5 numbers from the 1x bucket, so it randomly samples 5 from the 17 currently eligible 1x numbers.
  • 4x 1/5 means the generator needs 1 number from the 4x bucket, so it randomly samples 1 from the 5 currently eligible 4x numbers.

The exact constructive-fill order is fixed:

  1. Undrawn
  2. 1x
  3. 2x
  4. 3x
  5. 4x
  6. 5x
  7. 6x
  8. 7x
  9. 8x+

As numbers are picked, the generator fills the candidate main numbers first until there are 6 mains, then fills the remaining supplementary positions until there are 2 supps.

When constructive fill happens relative to other generation rules

The order matters:

  1. Exclusions are built first — including user exclusions, SDE1, HC3, and any Hard exclude zero-count buckets removals.
  2. Constructive fill runs next — bucket counts are used to seed the candidate.
  3. An early digit-width guard runs — if the seeded candidate already breaks the single-digit / two-digit target, that attempt is rejected immediately.
  4. Any remaining open slots are then filled by the normal weighted generator.
  5. Full-candidate constraints are checked after the 8 numbers are assembled.

This means the constructive bucket picks happen before the later weighted-fill influences such as:

  • Digit decade boost / punish
  • n-ending numbers max allowed (checked later as a hard constraint)
  • Single digit / two digit share
  • Selected-number boost
  • Monthly Repeat Bias
Constructive-fill picks themselves are not weighted by decade boosts or ending-digit boosts. Those weighting systems only influence the later remaining-slot fill stage if the candidate still has empty positions after constructive fill.

What happens when the selected counts already total 8

If the selected bucket counts add up to all 8 candidate positions, constructive fill can populate the entire candidate before the normal weighted generator runs.

In that case:

  • the candidate is driven almost entirely by the monthly bucket counts,
  • the generator randomly chooses within each eligible bucket, and
  • later weighting systems do not get a chance to choose additional numbers because there are no free slots left.

However, the finished candidate is still checked against later hard rules such as:

  • n-ending numbers max allowed
  • Single digit / two digit share
  • Odd/Even ratio
  • Maximum matches to last draw
  • Entropy / Hamming / Jaccard

So even a fully constructive candidate can still be rejected and retried.

Ending Digit Sequence Analyzer

The Ending Digit Sequence Analyzer checks whether the numbers in each draw form consecutive ending-digit runs. It works on the last digit of each number, not the full number itself.

Example: 12, 23, 34, 45 has endings 2, 3, 4, 5, so it contains a run of 2-3-4-5. Endings are treated circularly, so 8-9-0 and 9-0-1-2 also count as consecutive runs.

Each summary chip is shown as count · percentage. The percentage is based on the current analyzed window only. If the panel's Include supp (main + supp) checkbox is changed, these values can change because the analysis switches between main-only and main+supp numbers.

What the summary chips mean

ChipMeaning
Run ≥ 3 Counts draws whose longest ending-digit sequence is at least 3 digits long, such as 1-2-3 or 8-9-0.
Run ≥ 4 Counts draws whose longest ending-digit sequence is at least 4 digits long, such as 2-3-4-5.
Covered ≥ 4 Counts draws where the strongest ending-digit run explains at least 4 actual numbers in the draw. This is about how many numbers fall inside the run, not just how many distinct ending digits are in the run.
Run ≥ 5 Counts draws whose longest ending-digit sequence is at least 5 digits long, such as 8-9-0-1-2.

Run length vs covered numbers

Run length measures the number of distinct consecutive ending digits in the sequence. Covered numbers measures how many actual drawn numbers fall inside that strongest sequence.

Example: if a draw has endings 2, 2, 3, 4, 5, 8, the strongest run is still 2-3-4-5 with run length 4, but it covers 5 numbers because two numbers end in 2. That is why Covered ≥ 4 can be higher than Run ≥ 4.

A quick plain-English reading of the panel is: how often moderate ending-digit runs appear, how often long runs appear, and how much of each draw is explained by the strongest run.

Hot vs Cold Ranking

The Hot vs Cold Ranking panel compares three different ideas that are often mixed together when people say a number is “hot”:

  • Historical frequency — how often the number has appeared across the full loaded history.
  • Recent-window hotness — how often the number has appeared in the last selected number of draws.
  • Recency-weighted hotness — a whole-history score that still favours newer draws more heavily than older draws.

This makes it easier to compare the app’s long-run historical counts with the more recent “hot number” style rankings often shown on lottery websites.

Controls

  • Include supplementary numbers — switches the panel between main-only and main+supp analysis.
  • Recent window — chooses how many of the newest draws are treated as the recent comparison window.
  • Weighted half-life — controls how quickly older draws lose influence in the recency-weighted ranking.
  • Digits — restricts the table to all numbers, one-digit numbers, or two-digit numbers only.

How to interpret the rankings

  • A number can rank highly in Historical but not be currently hot.
  • A number can rank highly in Recent even if it is not one of the most frequent numbers overall.
  • Weighted sits between the two — it still uses the whole history, but recent draws matter more.
  • Hot score combines recent-vs-prior change and recency-weighted lift to label numbers as Hot, Warm, Neutral, Cool, or Cold.

Breakdown table column definitions

Every breakdown-table column header is sortable. Click once to sort by that column’s default useful direction; click the same header again to reverse it. Sorting changes only the table display order. It does not change hot/cold scores or candidate generation unless you also use the include/exclude row-selection controls.

  • # — the overall hot rank. A lower number means the number currently looks hotter by the panel’s combined scoring model.
  • Num — the lottery number itself.
  • Type — whether the number is 1-digit (1–9) or 2-digit (10–45). This matches the Digits filter.
  • Status — the label assigned from the hot score: Hot, Warm, Neutral, Cool, or Cold.
  • Hist count — how many loaded draws included that number across the full history currently in the app.
  • Hist rank — the number’s rank when sorted by full-history appearance count. Lower rank means more frequent historically.
  • Recent N — how many times the number appeared in the most recent window, where N is the selected recent-window size (for example, 20 draws).
  • Recent rank — the number’s rank when sorted by recent-window appearances. Lower rank means hotter in the current recent window.
  • Prior rate — the hit rate in the older comparison window before the recent window. This is the baseline used to judge whether the number has sped up or cooled off.
  • Recent Δ — the change between the recent hit rate and the prior hit rate, shown in percentage points. Positive values mean the number is appearing more often recently; negative values mean it is appearing less often recently.
  • Weighted rate — the number’s whole-history hit rate after applying recency weighting, so newer draws count more than older draws.
  • Weighted rank — the number’s rank when sorted by weighted rate. Lower rank means stronger recency-weighted hotness.
  • Hot score — the combined score used to produce the overall hot/cold ordering. It blends recent-vs-prior change with recency-weighted lift, so higher positive values are hotter and lower negative values are colder.
  • Generation — whether the number is currently selected for forced inclusion, forced exclusion, locked by User Exclusions, or not selected from this table.

If you want the quickest reading: numbers near the top usually combine a strong Recent rank, a positive Recent Δ, and a strong Weighted rank. Numbers near the bottom usually show the opposite pattern.

Month-end carry-over

The Month-end carry-over card tests a specific hypothesis: numbers that finish a month undrawn may be more likely to appear early in the next month.

How the analysis is built

  1. For each completed month in the active window, the app builds that month’s month-end undrawn set — the numbers not seen anywhere in that month under the current mode.
  2. It then checks the first 3 draws of the next consecutive month.
  3. If a month-end undrawn number appears in those early next-month draws, it counts as an early carry-over hit.
  4. Non-consecutive month gaps are skipped rather than treated as true carry-over transitions.

What the headline stats mean

  • Transitions — how many consecutive month-to-month boundaries were actually evaluated.
  • Month-end undrawn avg — the average size of the month-end undrawn set across those transitions.
  • Early-next-month hit rate — the share of month-end undrawn instances that were drawn within the first 3 draws of the next month.
  • Baseline — the ordinary per-slot draw rate over those same early-next-month draws.
  • Lift — the early-hit rate divided by baseline. Values above 1.00x suggest the month-end undrawn set was drawn early more often than a random number would be.
  • 95% range — the observed transition-to-transition range for early carry-over hit counts.

How to read the number lists

  • Best-supported early next-month flips — numbers that most often moved from month-end undrawn into an early next-month draw.
  • Most persistent into next month — numbers that tended to remain undrawn even after the month changed.
  • Early-hit timing — shows whether those flips happened more often in draw 1, draw 2, or draw 3 of the next month.
The analysis uses the active window only. If the window starts or ends mid-month, the boundary months may be partial, so full-history windows usually give the cleanest month-end interpretation.

How the shortlist is calculated

  • Scope: mains + supplementary numbers. This is appearance evidence from the full 45-number draw pool, not main-number-only probability.
  • Baseline: before a draw, a number has an 8 / 45 = 17.8% chance of appearing somewhere in the eight drawn numbers.
  • Strict drought state: the default view includes only numbers whose full-history current drought is at least six draws.
  • Strict ranking: rows are ranked first by full-history current drought, then by how mature that drought is against the number's own completed 6+ drought episodes, then by episode frequency and empirical hazard support.
  • Empirical hazard mode: after each historical draw, the app records each number's drought length k, then checks whether that number appeared in the next draw.
  • Smoothing: the empirical rate adds two baseline-prior trials to stabilize sparse drought lengths. This avoids overstating rare k values that have only a few observations.
Truthfulness note: this shortlist is an empirical diagnostic, not a guarantee and not a calibrated main-number prediction. Strict rank is a disciplined drought-severity ranking; empirical rate is supporting evidence, not a promise that the number is "due."

Most Likely NOT Drawn / Exclusion Risk Ledger

Most Likely NOT Drawn is now an observe-only Exclusion Risk Ledger. It ranks the 45 numbers by estimated draw risk and shows which numbers look least risky to exclude at the selected risk budget. It does not force candidate-generation exclusions.

Windfall All History definition: MLND ignores WFMQYH and uses real all-history evidence after excluding the opening partial month 2024-05. The draw history still displays that month, but Windfall excludes it from baseline-style calculations because it contains only part of the first historical month.

The default scope is mains + supps, because the statement “37 numbers will not be drawn” refers to the eight numbers that appear across the full draw result. Mains-only mode is available for diagnosis, but it answers a different question.

Risk budget controls how many numbers the ledger proposes as low-risk exclusions. A 37-number exclusion budget leaves exactly eight allowed numbers, so it is mathematically equivalent to proposing an eight-number draw universe. Smaller budgets are less aggressive and usually carry lower false-exclusion risk.

Random baseline: walk-forward validation trains only on draws before the test draw, then compares MLND’s false exclusions against a random exclusion set of the same size. For example, random 37-of-45 exclusions against an eight-ball result are expected to wrongly exclude 37 × 8 ÷ 45 = 6.58 drawn numbers. MLND only deserves trust when it beats that random baseline out of sample.

Important: MLND is evidence and calibration, not clairvoyance. A number listed as low-risk can still appear in the next draw.

Prediction Journal & Scorecard

The Prediction Journal & Scorecard is an observe-only validation panel. It lets you write down your own hypotheses before the next draw, then scores them later against real draw history. It does not influence candidate generation, candidate ranking, filters, forced numbers, or any weighting system.

Purpose: the journal is for learning whether your own observations are improving over time. It is deliberately separate from generation so the saved record stays honest.

New Prediction draft button

The panel is closed by default. Use the New Prediction button in the panel heading to open it and start a draft from the current app setup.

Windfall copies values into the form only where they fit the journal's scoring fields. For example, a single selected odd/even ratio can prefill Odd/even ratio; User Selected and forced/boosted inclusion numbers can prefill Numbers; and active Acceptance Needs counts can prefill Target draw bucket-origin mix when the counts fit inside the 8-ball next-draw limit.

The draft also writes a context note listing important setup values such as WFMQYH, SDE1, HC3, selected ratios, user-selected numbers, forced inclusion sources, forced exclusions, scoring influence, and selected-number boost state. Review the draft before saving. The button is a time-saver, not an automatic prediction.

How to fill in a journal entry

For a new user, the most important rule is simple: fill in only the prediction fields you genuinely want to test. The form is intentionally flexible. You do not need to complete every field, and a notes-only entry is valid if the observation is qualitative.

  1. Check the anchor latest draw. This is the latest real draw currently loaded. The entry is saved as a prediction made after that draw.
  2. Choose the target window. Use Next draw for a single immediate prediction, Next 3 draws for a short sequence idea, or Rest of current month for a month-stage hypothesis.
  3. Add the clearest prediction first. Examples: Odd/even ratio 2:6, Numbers 7, 14, 22, 31, Terminal digits 1, 4, 9, Confidence 65.
  4. Use target draw bucket-origin mix when your prediction is about where the drawn balls will come from. Example for Next draw: Undrawn 3, 1x 4, 2x 1 means you expect 3 of the 8 drawn balls to come from numbers currently undrawn this month, 4 from numbers currently drawn once, and 1 from numbers currently drawn twice. Do not enter the whole monthly bucket state here.
  5. Use shape checks for broad composition ideas. Example: Single-digit 1, Double-digit 7, Sum min 150, Sum max 210.
  6. Use recorded diagnostics for specific pattern ideas. Example: U/D/F ratio 3/2/3, Repeat count 1, ±1/±2 count 2, Drought count 1, Carry-over count 0.
  7. Add notes while the reasoning is fresh. Example: "Testing whether SDE1 plus HC3 looks stronger on D3 after a low-repeat previous draw."
  8. Save before the target draw arrives. Once the relevant real draw appears in history, the entry locks so it cannot be rewritten after the result is known.
Helpful habit: saving at least one prediction entry per draw gives the app creators a clean audit trail. Saving more than one entry is even better when each entry tests a different idea, such as ratio, candidate numbers, monthly buckets, carry-over, or ±1/±2 behaviour. Over time, this record can help refine Windfall's algorithms and improve its possible winning-entry logic without relying on memory or hindsight.

How entries are anchored and locked

  • When you save an entry, it is anchored to the latest real draw currently loaded in history.
  • The app also captures the current State Preset-style setup snapshot, including WFMQYH, generation controls, hard filters, selected ratios, selected/excluded numbers, and other preset-managed switches.
  • You can edit or delete the entry while no target draw has arrived yet.
  • If you edit an entry before it locks, the setup snapshot is refreshed to the app state at the time of the latest save.
  • Once the first target draw appears in history, the entry locks and can no longer be edited. This prevents after-the-fact changes.
  • The panel uses real draw history for scoring, not the active WFMQYH filter. WFMQYH can help you form a prediction, but validation must use the actual next draw stream.

Saved setup provenance

Each entry displays a compact Saved setup summary, such as the WFMQYH mode, selected odd/even ratios, scoring influence, carry-over bias state, core hard-filter state, and selected/excluded number counts. The full setup snapshot is also stored inside the journal export so later analysis can compare prediction quality under different app configurations.

Important: the saved setup snapshot is provenance. It does not change candidate generation, does not alter scoring, and does not make the prediction more or less true by itself.

Previous ±1 Neighbour Backtest

The Previous ±1 Neighbour Backtest panel tests whether a draw tends to include numbers that are exactly one step above or below numbers from the preceding draw. The panel itself is an observe-only diagnostic and does not alter candidate generation; the separate default-off Latest Draw ±1 Constraint Builder in Candidate Generation Influences is where you can deliberately force selected adjacent target numbers into generation.

How the neighbour set is built

For each number in the previous draw, the app creates up to two adjacent targets: n - 1 and n + 1. Boundary numbers only produce one target, so 1 produces 2 and 45 produces 44.

If two previous-draw numbers nominate the same adjacent target, that target is marked as a duplicated neighbour. For example, previous numbers 33 and 35 both nominate 34.

What the panel reports

  • Observed vs random compares the average number of ±1 hits per next draw with the exact random expectation for the available neighbour target count.
  • Duplicated neighbours compares the duplicated-target hit rate with the ordinary random single-number hit rate.
  • Soft-rule candidate check samples candidate pools and asks whether candidates ranked by historical neighbour-shape fit score better than random candidates.

Anti-lookahead rule

For each historical target draw, the soft-rule model is calibrated only from transitions that occurred before that target draw. The target draw and all later draws are hidden from the calibration step.

Truthfulness note: a positive result here is diagnostic evidence, not a guarantee. The panel is intentionally separated from generator controls until backtesting shows that the signal improves candidate quality out of sample.

Key Analysis Findings

Observed candidate-sample diagnostics (analysis of 71,000 generated candidates)

  • 2x bucket count had the strongest observed association in the internal candidate sample.
  • Nrr showed a monotonic association in that sample, but should be treated as an uncalibrated rarity diagnostic.
  • Conv direction has zero predictive value — positive and negative Conv candidates win at identical rates.
  • Conv magnitude (|Conv|) carries a modest 2.25× lift.
  • IDM, Rdy, Conv are highly correlated with each other (same top-1,000 candidates) — using all three adds little independent signal.
  • Stage IDM is deliberately labelled as an uncalibrated stage-alignment diagnostic until it has its own walk-forward evidence.
  • OGA% is only reliable when the generation window contains ≥ 10 draws.
